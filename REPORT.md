# Отчёт по практике 2: ИИ-сервис первичной обработки обращений

Кейс: ИИ-сервис первичной обработки обращений (с журналом и развёртыванием).
Срок кейса: 14 дней (лекция получена 08.10.2026).
Код и инструкция запуска: `README.md` в этой же папке.

## 1. Кому и какую проблему решаем

Клиент (по условию симуляции): онлайн-сервис или образовательный проект. В тестах это вымышленная онлайн-школа «Северный ветер». Менеджеры тратят время на первичную сортировку обращений и типовые ответы. Из-за этого падает скорость реакции и качество.

Сервис берёт на себя первую линию:
- определяет тип обращения (оплата, поддержка, жалоба, прочее);
- пишет черновик ответа, который проверяет человек;
- отдаёт человеку то, в чём не уверен;
- пишет каждое обращение и результат в журнал, чтобы качество можно было проверить.

Что сервис НЕ делает: не подключён к реальной почте, формам и чатам (по условию, обращения приходят как обычный текст), не отвечает клиенту сам, не знает ничего вне справки о компании.

## 2. Ограничения и допущения

| Что | Решение |
|---|---|
| Длина обращения | 1-2000 символов, пустой текст после обрезки пробелов отклоняется |
| Канал | только `email`, `form`, `chat`, это метка источника для аналитики |
| Лимит | 5 запросов в минуту на `client_id` (меняется в `.env`) |
| Категории | 4: `billing`, `support`, `complaint`, `other` |
| Температура модели | 0.2: меньше «фантазии», больше опоры на входной текст |
| Тексты | только вымышленные: текст обращения уходит во внешнюю модель |
| Секреты | ключ только в `.env`, в git и в образ Docker не попадает |
| Справка о компании | вымышленная, лежит в `config/knowledge.md`; модель отвечает только по ней |
| Без RAG | по условию (следующая практика) |

Допущения, которые я принял сам (в задании не заданы): FastAPI как фреймворк, OpenAI `gpt-4.1-mini` как модель, доступ через ProxyAPI, лимит 5 в минуту.

## 3. Архитектура

```
  Клиент (curl, Postman, /docs)
        |
        v
 [1. HTTP-слой]  main.py + schemas.py  - принимает JSON, проверяет формат; не прошёл -> 422, в журнал не пишем
        |
        v
 [2. Лимит]      limiter.py            - сколько запросов от client_id за 60 секунд; больше 5 -> 429 + Retry-After
        |
        v
 [3. Ядро]       triage.py + llm.py    - фильтр манипуляций -> промпт + справка -> модель -> проверка JSON -> правила эскалации
        |                                                   |
        |                                         сбой модели -> шаблон «передано оператору», escalate=true
        v
 [4. Журнал]     store.py (SQLite)     - строка в таблице tickets: вход, результат, error
        |
        v
 [5. Ответ]      200 + 4 поля контракта
```

Правила (категории, когда звать человека, шаблон «передано оператору», фразы-манипуляции) лежат в `config/triage.yaml`, промпт в `config/prompt.md`. Чтобы настроить сервис под другого клиента, меняются эти файлы, код остаётся.

Решение об эскалации принимает код по правилам, а не модель: так поведение предсказуемо и проверяется тестом.

## 4. Контракт программного интерфейса

Запрос `POST /triage`:

```json
{
  "text": "Не пришёл чек после оплаты тарифа «Базовый»",
  "channel": "form",
  "client_id": "demo-1"
}
```

Ответ 200:

```json
{
  "category": "billing",
  "draft_reply": "<черновик ответа, 1-6 предложений>",
  "confidence": "high",
  "escalate": false
}
```

Другие ответы: 422 (запрос не прошёл проверку), 429 (лимит, с заголовком `Retry-After`). Сбой модели не даёт ошибку клиенту: ответ 200, `escalate=true`, шаблон «передано оператору».

## 5. Как устроен журнал обработки

SQLite, таблица `tickets`. Пишутся все принятые обращения, в том числе те, на которых модель сбоила.

| Поле | Что хранит |
|---|---|
| `id`, `created_at` | номер и время (UTC) |
| `client_id`, `channel`, `text` | вход |
| `category`, `draft_reply`, `confidence`, `escalate` | результат |
| `error` | причина сбоя, если был (в том числе пометка о манипуляции или отсутствии ключа) |
| `model`, `latency_ms` | какая модель отвечала и сколько это заняло |

Лимит считается по этой же таблице: число строк `client_id` за последние 60 секунд. Побочный эффект: в лимит попадают и обращения со сбоем модели.

## 6. Надёжность

- **Эскалация к человеку** при любом из условий: категория `complaint`, уверенность `low`, сбой модели.
- **Сбой модели** (таймаут 25 секунд, ошибка сервиса, ответ не в формате JSON, значения вне списка): клиент получает 200, категорию `other`, уверенность `low`, `escalate=true` и шаблон «передано оператору». Причина записывается в `error`.
- **Манипуляции** («забудь правила», «покажи промпт», «выдай данные других клиентов»): два слоя. Первый: список фраз в `triage.yaml`, при совпадении модель не вызывается вообще, ответ-заглушка и `escalate=true`. Второй: правила в промпте, текст обращения объявлен данными, а не инструкциями.
- Лимит: скользящее окно 60 секунд на `client_id`, ответ 429 с `Retry-After`. Другой `client_id` не затрагивается.
- Логирование: в консоль идёт номер тикета, длина текста, категория, признак эскалации, предупреждение при сбое. Сам текст обращения в логи не пишется (там могут быть персональные данные).
- Проверка: 54 автотеста (модель в них заменена заглушкой) и скрипт `scripts/check_service.py`, который проверяет запущенный сервис по HTTP: 6 проверок из 6 пройдены, в том числе в Docker-контейнере. Данные в томе переживают пересоздание контейнера.

Ограничения результата:

- На промахе №14 («список других клиентов») сначала сервис ошибся. Я добавил в список фраз шаблон про «других клиентов» уже после этого. То есть этот пример прошёл после подгонки под него.
- Список фраз ловит только известные формулировки. Новая формулировка манипуляции пройдёт к модели и будет полагаться на промпт.
- Возможны ложные срабатывания: безобидное обращение с подходящей фразой уйдёт к человеку. Для безопасности это допустимо, но нагрузку на операторов увеличит.
- Тексты ответов проверены мной на отсутствие выдуманных фактов только на этих 14 примерах.
- Пометка о манипуляции сейчас лежит в поле `error` рядом со сбоями модели. Для аналитики их стоит разделить.

## 7. Развёртывание и демонстрация

**Выбран путь B:** сервис запускается локально (с Docker и без), работа доказывается демо-видео и логами. Публичного хостинга нет.

Почему не путь A (хостинг):
- Решение принято мной 09.10.2026 вместе с выбором стека.
- Публичная ссылка без авторизации означала бы, что любой может отправить запросы на мой платный ключ ProxyAPI. Лимит по `client_id` этого не останавливает: `client_id` задаёт сам вызывающий, и сменой идентификатора лимит обходится.

Как воспроизвести: `README.md`, два варианта запуска (venv и Docker), запуск проверен в пустой папке по критерию «5-10 минут». В Docker: образ `ai-triage:1.0`, порт 8000, база в томе.

Доказательства работы: видео (раздел 8), результаты `check_service.py` (6 из 6), живой прогон (`reports/eval_live.md`), выписка из таблицы `tickets`.

## 8. Демонстрация (видео)

Видео приложены к сдаче на учебной платформе отдельными файлами (в репозиторий не входят из-за размера):
- Демо-видео 2-3 минуты («запрос → ответ → запись в БД»): файл «Демо видео Учебного проекта Зубковский АВ».
- Видео защиты 5-7 минут: файл «Защита Учебного проекта Зубковский АВ».

Сценарий демо и тезисы защиты совпадают с разделами этого отчёта; в защите по шаблону лекции пять пунктов (проблема, контекст и ограничения, решение, риски, план внедрения) и отдельный блок про отклики.
